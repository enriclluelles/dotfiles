# One evals from the CLI

`one-evals` is the platform's command-line client (`architecture/cli.md` in the one-evals repository). `one-evals help --json` is its whole contract, commands, flags, the routes they call, rows, columns, formats and exit statuses: run it once and work from it.

## Setup

- Install: the platform's Agent access page gives a prompt that does it; or `GOPRIVATE=github.com/factorialco go install github.com/factorialco/one-evals/backend/cmd/one-evals@latest`; `make cli` in the repository builds `backend/bin/one-evals`.
- Sign in: `one-evals login` opens the browser at the platform's CLI sign-in page, where a **person must click Approve**. Tell the user that before running it, run it, and wait: it returns once they approved, or after five minutes. The CLI then carries the browser's session, which ends when the browser's does, 12 hours after the person signed in, and acts as that person with their role, viewer, editor or admin; `whoami` shows both.
- Exit status 3 means not signed in or expired: run `one-evals login` again and ask the person to approve. 2 is a usage error, answered with the command's help; 1 is the API's or the network's error, with its message on standard error, a refusal of the person's role among them; 4 is `wait --timeout` running out while the batch still runs.
- The local platform, `--url https://evals.k8s.orb.local`, needs no sign-in.
- The CLI compares its build with the platform's once a day and replaces itself, and this skill, when they differ; `one-evals update` does it now, `one-evals version` shows both builds.

## Reading

| Command | Gives |
|---------|-------|
| `evals [--tag T]… [--untagged G] [--intent I] [--module instance\|filesystem\|screen\|page\|none] [--result passing\|flaky\|failing\|regressed\|fixed\|none] [--search S]` | The library's evals with their tags as `group:name`, intent, environment modules, current version and what its last ten runs on track say, passing, flaky, failing, regressed or fixed, with how many failed; `--tag` more than once keeps, within a group, any of them and, across groups, all of them, so `--tag business-logic --tag team:payroll` is the payroll team's business-logic evals; `--untagged team` those without a Team tag |
| `tag-groups`, `tags` | The tag groups in their order, Kind, Team, Status, Topic and those admins added, each taking one tag per eval or several, with their tags and how many evals carry each; the tags of every group |
| `eval <id> --format text` | An eval's current version as the `eval.yaml` an export writes: scenario, input, rule, criteria, examples; `--version N` another |
| `history <eval>` | The eval's runs across versions, newest first: batch, agent tag, result, failed criteria, cost |
| `batches [--agent A] [--kind ci\|scheduled] [--started-by W] [--on-track] [--limit N]` | The batches, newest first, with progress, pass rate and cost; a scheduled batch is started by its schedule, `--started-by` its name |
| `schedules`, `schedule <name>` | The schedules with what each runs, its days, time and time zone, its next start and its last; one with its starts, newest first, each with its batch or why it was skipped or failed |
| `batch <number>` | A batch against its baseline, the agent's runs on track before the batch, `main` for One: the evals counted in `outcomes`, regressed, fixed, flaky, failing, passing, and errored or still to come, its steps, time and cost per run against the baseline's in `against`, what it ran with and its cost, and a row per eval, the regressed first, with its `outcome`, its baseline's state and its pass rate. Report the regressed and fixed, not the pass rate |
| `compare <a> <b> --changed` | Two batches, or two agent versions named `agent@digest`, on the evals both ran: the evals counted by what happened to them in `outcomes`, regressed, fixed, flaky, rubric (another eval version) and unchanged, each side's pass rate, steps, time and cost per run over them in `figures` (`--format json`), and the evals that are not unchanged, the regressed first, each with its `outcome`, its recent runs on the after's agent's track and each side's pass rate, steps and cost per run. A change of result is regressed or fixed only when the recent runs point the same way, flaky when they flip or go the other way: report the regressed and fixed, not the pass rate, which flaky evals move. Steps, the agent's model calls, rather than time, which moves with the provider and the cluster |
| `run <id> --format text` | A run as a transcript: input, tool calls, final message, artifacts, verdicts with the judge's reasoning, usage and cost; tool inputs and outputs cut at 500 characters unless `--full` |
| `dashboard [leaderboard\|unranked\|series\|latest\|failing\|flaky\|regressed\|most-steps\|most-steps-in-window\|slowest\|slowest-in-window\|costliest\|costliest-in-window\|failing-criteria\|tags\|intents] [--tag T]… [--intent I] [--agent A\|--agent agent@digest]` | The dashboard on a suite, every active eval unless tags, by the same rule as `evals`, or an intent narrow it; `tags` is the pass rate by tag within each group: the agent versions, an agent at an image digest, ranked from 90% of the evals the most-run version ran, with their cost and time per run, each agent's line over time, and the agent's failing, flaky and regressed evals over their last ten runs, or one version's alone with `--agent agent@digest`; the evals with the most steps, the slowest and the costliest by their latest run, `-in-window` by the worst of the ten |
| `activity [--who EMAIL] [--area library\|snapshots\|batches\|settings\|access] [--eval ID] [--schedule NAME] [--search NAME] [--limit N]` | Who did what on the platform, newest first: an entry per change or action with the records it touched and what changed in each |
| `intents`, `agents`, `secrets`, `sandboxes`, `renderers`, `screen-widths`, `judges`, `providers`, `prices`, `limit`, `members`, `clients`, `snapshots`, `backend-versions` | The registries and the settings: also the values the flags take |
| `get <path> [name=value …]` | Any `GET` route of the API, for what has no command |

Batches are named by their number, `26`, agents by their name, tags by their name, or as `group:name` where two groups have it, `topic:leaves`, tag groups by their name, judge models by their name, schedules by their name; evals and runs by their ids.

## Acting

What the person's role allows: an editor or an admin starts batches, imports, archives and restores evals, dry-runs, runs workshops and registers and duplicates agents, an editor editing and deleting only the agents they registered; an admin also changes the settings; a viewer only reads.

- **Batches.** `start --tags business-logic,team:payroll --agent One --attempts 3 --preview`, the tags by the same rule as `evals`, lists the evals a batch would run and those it leaves out; the same without `--preview` starts it, `--tag` naming an image tag other than the agent's and `--renderer-tag` a tag of the agent's renderer other than its own, a pull request's renderer for instance. `--random 100` in place of `--tags` draws 100 evals at random from every active eval; its preview says the seed, and `--seed` with that seed starts the batch on the evals it listed. `--wait` follows it to its end; an agent whose commands time out runs `wait <batch> --timeout 9m` again while it exits with 4. `cancel <batch>` drops its queued runs and stops those in flight. `retry <batch>` puts its errored runs back in the queue to run again in the same batch, at its digest, backend and judge, so a batch a platform failure left short gets its results; `--wait` follows it.
- **Schedules.** `schedule add Nightly --all --agent One --days weekdays --at 03:00 --tz Europe/Madrid` starts a batch of the selection on those days at that time, the selection as `start` takes it; it skips a start while its last batch runs, and when the agent's image is the one its last batch ran unless `--always`. `schedule edit <name>` changes what its flags give, `schedule pause|resume|start|delete <name>` pauses it, resumes it, starts its batch now or deletes it, its batches staying; `activity --schedule <name>` says who created and changed it.
- **Evals as files.** `export --tag team:payroll --out evals` writes the evals the tags select, `export` alone the whole library: `library.yaml` with the tag groups, and a directory per Kind tag, `untagged` for the evals without one, each eval a directory with its `eval.yaml`, its tags by group, and its files; edit them; `import evals --dry-run` reports what would be created, updated or left, and says on standard error the tag groups and tags it would make; `import evals --note "what changed"` imports. The directory above an eval is its Kind tag, so moving the eval's directory changes its Kind. An eval judged on the screen holds a screen in its environment, the chat's width, `screen: {width: 360}` for the side panel as Factorial opens it, `screen: {width: 712}` at its widest, among the widths `screen-widths` lists: a screen criterion needs it, and the run renders the answer at that width. An eval whose message is sent from a page of Factorial, a button on an employee's page or a request about "this" record, holds a page, `page: {path: /time-off/employees/8, title: Laura López · Time off}`, the path in the app without an origin and the title optional: the run gives the agent the page's URL in the instance it leased. A message a card sends with context the chat never shows, as the Balance card's "Explain this to me" does, holds it as `hiddenContext: |` beside `input:`, the context as the card writes it; the agent gets it apart from the text, and the judge does not. The ids in `eval.yaml` keep the same evals; a directory without one makes a new eval, or updates the eval of that name, names being unique in the library.
- **Tags**, as an editor: `evals tag <id,…> --add team:payroll --remove topic:draft` adds and removes tags on the evals named; a tag written as `group:name` is made on first use, and a tag of a group that takes one, Kind, Team or Status, replaces the eval's. As an admin: `tag-group add Area --one`, `tag-group rename`, `tag-group order <group> <position>`, `tag-group delete` for a group with no tags; `tag add <group> <name>`, a tag no eval carries yet; `tag rename <tag> <name>`, which merges it into the tag of that name when its group has one, `tag move <tag> <group>`, `tag channel <tag> <channel>`, the Slack channel a Team tag's regressions go to, `tag delete <tag>`, which takes it off every eval; `teams apply library/team-channels.yaml --dry-run`, then without `--dry-run`, sets the Team tags' channels and tags the evals the file names that have no Team tag. The Kind group names the export's directories: it cannot be renamed, deleted or made to take several tags.
- **Archiving**, as an editor: `evals archive <id,…>` takes the evals named out of the library's default view and of every selection, their versions, runs and results kept; `evals restore <id,…>`, or `unarchive`, makes them active again. An id the library lacks refuses the whole command, and standard error says how many changed and which were in that state already. `evals --archived` lists the archived ones; nothing deletes an eval.
- **Rubrics.** `dry-run <eval> --attempts 3` judges each of the current version's examples against the criteria of its kind, a verdict per line as it arrives with the example's name and whether it agrees with the example: a passing example should pass every criterion, a failing one fail the criteria it names and pass the rest. A criterion that disagrees with an example or wavers shows before any agent runs. Every dry run is kept with its eval, its id on the first line: `get /api/evals/<id>/dry-runs` lists the eval's, newest first, with their counts and cost, and `get /api/dry-runs/<id>` gives one whole, its parts and verdicts, so the last one is read again without judging again. It is judged on the platform: a command that times out or is interrupted stops only the following, the dry run goes on, and `dry-run cancel <id>` cancels it. An example is one part of an output, a message, a file, a screen or the instance's responses, judged by the criteria of its kind only; a screen criterion judges a screenshot of the response, which a run renders as Factorial's chat shows it, widgets included, with the renderer at the batch's backend commit; `run <id> --format text` names the response's widgets and the screen's file.
- **Workshop**, an eval's data made in Factorial's own UI or through its GraphQL API. `workshop start <eval> --wait` leases an environment from the current version's snapshot, or `--snapshot <id|name>`, at main for four hours, one per person; `workshop` shows it with its link, state and time left; `workshop accounts` lists who to sign in as; `workshop sign-in <email>` opens that account's sign-in link in the person's browser, where **the person** changes the data: tell them, and wait until they say they are done. When the person asks you to make the data, `workshop graphql` sends a GraphQL request to the instance's API as an account, the default one or `--as <email>`: the query as the argument or on standard input, one operation per request since Factorial takes no operation name, `--variables '{…}'` or `--variables @vars.json`. It prints the instance's response as it came, `data` and `errors` alike, and exits 0 whenever the instance gave a GraphQL response, so read `errors`, and a mutation's own `errors` field where it has one. The link signs anyone in as that account, so never ask for `--no-browser`, which prints it, unless the person wants it. `workshop snapshot --name "…" --description "…"` captures the data, `workshop save --note "…"` saves the eval's next version on that snapshot, whom it acts as kept unless `--acting-user <email>`, or `--acting-company <id>` for an agent that acts for the company and never as a person, and `workshop release` frees the environment; `--discard` drops changes no snapshot holds, only when the person said so. `workshop extend` adds an hour.
- **Debugging the workshop**, when the instance does something unexpected. `workshop containers` lists the environment's containers, `app/backend` the monolith with its requests, jobs and errors; `workshop logs [container] [--since 10m] [--tail N]` prints a container's log since the lease attached, the last 100 lines by default. `workshop exec [container] -- <command…>` runs one command, `app/backend` unless named, input piped to it passed on, and exits with the command's status: `one-evals workshop exec -- bin/rails runner 'puts Employee.count'`. `workshop shell` needs a person at a terminal: never run it.
- **Agents**, as an editor: `agent duplicate <agent> --name N --tag T --unset VAR --renderer R` registers a copy of an agent changed by the flags, its variables taking the same secrets; `agent register --image I --tag T --env MODE=eval --secret API_KEY=<secret>` makes a variable take one of the platform's secrets by its name, which `secrets` lists with the agents that take them, and nobody types the value; `agent edit` and `agent delete` work on the agents the person registered, any agent for an admin.
- **Settings**, as an admin. `price set <model> --input 2 --cached 0.1 --output 10` adds or edits a model's price, dollars per million tokens; `limit set 8` or `limit reset`; `member add <email> --role editor`, `member role <member> admin`; `agent edit <agent> --tag 2.5.0 --memory 2048 --env MODE=eval` changes only what it names, `--sandbox <image> --sandbox-memory 4096` switches its sandbox on with a sandbox image and `--no-sandbox` off, `--renderer <renderer>` picks the renderer that draws its widgets and `--no-renderer` none; `sandbox add`, `sandbox edit <image> --tag T`; `renderer add --name N --image I --backend-commit` or `--tag T`, `renderer edit <renderer> --memory 3072`; `secret add <name>`, `secret set <secret>`, `secret rename <secret> <name>`, `secret delete <secret>`; `provider add`, `judge add`, `judge default`, `client issue`. A secret's value never goes on the command line: `secret add` and `secret set` read it from the first line of standard input, and `provider add` or `provider edit --key` read the key there. Settings change the platform for everyone: change what the user asked for, and say what changed.

## Working well

- Keep answers small: `--format tsv` prints each command's main columns, `--fields a,b.c` names others; `jsonl` prints one row per line. `--format json` without `--fields` is the API's full answer.
- Start wide, then narrow: `dashboard` or `batch <number>` for the shape, `compare` for what changed, `run <id> --format text` to read why a run failed.
- Batches and dry runs cost money: every attempt of every eval runs the agent and the judge's model. Preview a batch, choose the attempts deliberately, start one or retry a batch's errored runs only when the user asked for it, and report its `cost` afterwards.
- An import changes the library for everyone: dry-run it, show the user the report, and import only what they asked for.
- Archiving takes evals out of every batch and the dashboard's suites for everyone: archive only the evals the user named or agreed to, listed to them first when a filter chose them.
- A schedule spends on every start until someone pauses it: add or change one only when the user asked, with the runs it makes per start, its evals times its attempts, said first.
- Cancel only the batches and dry runs you started.
- A workshop holds one of one-envs' environments until it is released or its four hours end: release the one you started once its snapshot is saved.
- Make data with `workshop graphql`, not with `workshop exec` and the Rails runner: a mutation goes through Factorial's validations as the UI does and leaves the environment safe. Find the mutations and their inputs by asking the schema for the types you need, never the whole schema: `{ __schema { mutationType { fields { name } } } }` lists the domains' namespaces, `{ __type(name: "teamsMutations") { fields { name args { name type { name kind ofType { name } } } } } }` a namespace's mutations, and queries the same way from `queryType`; act as the account the person names, or the default one, and read back what you made with a query before taking the snapshot.
- Read a workshop's logs first. Run `workshop exec` only when the user asked you to debug the instance, and say first that the first command makes the environment unsafe, so one-envs deletes it at release; snapshots are taken as before. A command ends when you stop waiting for it, at your own time limit too: start one that may take longer detached, `workshop exec -- sh -c 'nohup <command> > /tmp/<task>.log 2>&1 &'`, and read its file with `workshop exec -- tail -n 50 /tmp/<task>.log`.
